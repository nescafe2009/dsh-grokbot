# 长任务与多轮接续

阶段计划描述整个工程；一次成员派发只描述一个可独立检查的产物及其验收标准。`team_send_task` 必须提供 `task`、`deliverable`、`acceptance`；批量建项目时，有初始任务的成员也必须提供后两项。已有直接 inbox 请求保持兼容，但执行时同样收到小任务和检查点约定。字段齐全不能证明任务规模合理，幕僚长仍需审核范围。

## 执行策略

- 默认 `jobHardTimeoutMs: 0`，不因总时长或沉默自动停止。用户仍可停止任务，停止后记录 cancelled，保留部分回复。
- `jobReviewAfterMs: 1800000` 是进展检查提醒，非截止。旧 `jobTimeoutMs` 仅兼容为检查阈值。
- `jobIdleWarningMs: 900000`：没有新的模型输出或工具事件时提示。区分等待工具、等待审批、无可见进展；等待审批不触发停滞提醒。长工具未返回不代表工具死锁。
- 每15秒观察一次会话事件，增量读取并保存 `progress.json`，同时更新项目看板。提醒按状态变化去重并受最短15分钟窗口限制，取消原每4分钟的群聊心跳，不向运行中的成员注入额外任务、不自行重派。
- 如运营者明确设置大于0的 `jobHardTimeoutMs`，才执行硬截止，并将部分结果记为失败。该配置不开放给 Bot 通过工具修改。宿主、模型提供方和单个工具自身的限制仍可能结束执行，本优化不绕过它们。
- 输出活跃不等于工作正确；不使用token流或时间直接判定业务完成。没有自动终止时，真正卡住的工具可能继续占用执行槽，需用户检查/停止。

## 检查点与接续

成员在有效里程碑及结束前调用 `task_checkpoint`，原子保存已完成工作、文件、验证、剩余事项和阻塞。记录带 `verified:false`，最新检查点可跨重启保留；它不是文件快照或验证证明。没有调用工具则不能保证有语义检查点。

项目看板和幕僚长状态快照包含检查点；终态任务不再显示陈旧的运行进度。幕僚长先检查文件与验证证据，再拆分剩余任务、派发并用 `team_update_plan` 关联新jobId。不得因提醒或自动通知越过用户的阶段边界，也不得重复派发仍在运行/排队的任务。

任务失败保留部分输出。协调仅在有效回复成功写入群记录后确认；失败最多重试两次，耗尽后留待处理并提示。进程重启不会自动重放所有历史任务，避免重复副作用。共享工作区仍使用现有互斥执行策略，任务已派发不等于正在并行执行。

## 验证

`tests/job-progress.test.mjs` 用虚拟时间覆盖8小时持续输出、沉默、工具等待和审批；生产路由测试覆盖检查点持久化、用户停止、默认关闭硬截止和显式硬截止。检查点展示与跨终态读取分别由组件测试和项目看板测试覆盖。
